# maskrun

Запускайте команды с секретами из системного хранилища ключей — и держите
значения вне контекста вашего ИИ-агента для кода.

```bash
maskrun put myapp-database-url        # хранится в keyring, никогда на диске
maskrun run -- npm run dev            # внедряется в дочерний процесс, маскируется в выводе
```

```
$ maskrun run -- node -e 'console.log(process.env.DATABASE_URL)'
<masked:DATABASE_URL>
```

Один бинарник, никаких зависимостей времени выполнения, никакого демона. Linux,
macOS и Windows.

---

## Проблема

Перенести секреты из файлов `.env` в системное хранилище ключей — это лёгкая
половина. Трудная начинается, когда вашей оболочкой управляет ИИ-агент.

Внедрение секрета в дочерний процесс мешает агенту *читать хранилище*. Но оно
ничего не делает со значением, которое *возвращается из процесса наружу*:

- dev-сервер печатает строку подключения при старте
- `curl -v` повторяет заголовок `Authorization`
- трассировка стека несёт в себе DSN
- `psql` цитирует URL, к которому не смог подключиться

Любой из этих случаев помещает секрет в транскрипт, где он становится частью
диалога, истории терминала и всего, где этот транскрипт хранится.

maskrun закрывает этот путь и соседние с ним.

## Установка

**Linux / macOS** — скачивает готовый бинарник, проверяет контрольную сумму,
компилятор не нужен:

```bash
curl -fsSL https://raw.githubusercontent.com/furkanakyol/maskrun/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/furkanakyol/maskrun/main/install.ps1 | iex
```

**Через тулчейн Rust:**

```bash
cargo install maskrun
```

**Из исходников:**

```bash
git clone https://github.com/furkanakyol/maskrun
cd maskrun && cargo build --release
# бинарник в target/release/maskrun
```

## Быстрый старт

```bash
# 1. перенесите существующий .env в keyring — сперва посмотрите, потом прыгайте
maskrun import .env --dry-run
maskrun import .env

# 2. проверьте, что каждое имя из манифеста действительно на месте
maskrun status

# 3. запустите приложение без .env на диске
maskrun run -- npm run dev

# только теперь удалите .env
```

`import` пишет манифест `.maskrun` рядом с вашим кодом:

```
DATABASE_URL=myapp-database-url
JWT_SECRET=myapp-jwt-secret
```

**Этот файл содержит имена, а не значения. Коммитьте его.** Это тот самый
`.env.example`, который действительно что-то делает: `maskrun status` скажет
новому коллеге ровно то, каких секретов у него не хватает.

## Как это работает

Три механизма для трёх разных задач.

| Задача | Механизм | Что видит агент |
|---|---|---|
| Dev-сервер, миграция или CLI, которым нужен `DATABASE_URL` | `maskrun run` внедряет в дочерний процесс | маскированный вывод (`<masked:VAR>`) |
| Само значение — ротация ключа, вставка в панель управления | вы, в своём собственном терминале | ничего; тормоз отказывает |
| Знать, *какие* секреты существуют | `maskrun list`, `maskrun status` | только имена, никогда значения |

### Внедрение, а не чтение

Значения живут в keyring. `maskrun run` разрешает манифест, передаёт значения
ровно одному дочернему процессу и ничего не пишет на диск. Если какого-то
секрета не хватает, он откажется стартовать, вместо того чтобы поднять ваше
приложение с половиной окружения.

### Маскирование вывода

`run` и `exec` пропускают stdout и stderr дочернего процесса через фильтр,
который заменяет значения секретов на `<masked:VAR>`.

- Значения попадают в фильтр через **его окружение**, никогда через argv —
  argv читается через `/proc/<pid>/cmdline`.
- Маскирует как исходное значение, так и его написания в base64, в
  URL-кодировании и с экранированием обратными слэшами.
- Ловит значение, **разбитое между двумя записями**, так что секрет на границе
  сброса буфера не проскользнёт.
- Полные строки пропускает сразу, чтобы вывод dev-сервера не буферизовался,
  пока вы на него смотрите.
- Отказывается маскировать значения короче 6 символов и прямо об этом
  сообщает: маскирование `5432` испортило бы любое постороннее число в выводе.
- Код возврата, stdin и Ctrl-C доходят до дочернего процесса без изменений.

Включено по умолчанию в сессии ИИ-агента и всегда, когда stdout не терминал;
выключено в вашем собственном интерактивном терминале, чтобы сохранить цвета.
`--raw` принудительно выключает, `--mask` принудительно включает.

### Тормоз агента

```bash
maskrun install-guard        # регистрирует хук PreToolUse для Claude Code
```

Весь смысл хука в том, что **его применяет харнесс, а не модель**. Правило,
записанное в промпт, применяет модель — а значит, модель может сама себя от
него отговорить. От этого отговорить нельзя.

Он отказывает командам, которые поместили бы значение в транскрипт:

- `maskrun get`, `maskrun import`
- `secret-tool lookup/search`, `security find-generic-password`
- `--raw`, `MASKRUN_MASK=0`, `MASKRUN_ALLOW_READ=1` (отключение маскирования)
- `/proc/<pid>/environ`
- голый `env` / `printenv`, `Get-ChildItem Env:`
- чтение `.env` / `.envrc` — хоть через Bash, хоть файловыми инструментами
  агента

И не трогает обычную работу: `maskrun run`, `env VAR=x cmd`,
`cat .env.example`, `cat .maskrun`, `printenv PATH`, `ls -la .env`, `rm .env`.

`maskrun install-guard` встраивается в ваш существующий `settings.json`,
сначала делает резервную копию, идемпотентен, отказывается трогать файл, не
являющийся корректным JSON, а `--remove` всё отменяет. Другие харнессы:
запускайте `maskrun hook` как хук перед вызовом инструмента — он получает вызов
в виде JSON на stdin, см.
[integrations/claude-code](integrations/claude-code/).

Сам CLI применяет те же отказы, поэтому агент, работающий в харнессе без
поддержки хуков, всё равно не сможет выполнить `maskrun get`.

### Как направить агента, у которого нет механизма хуков

```bash
maskrun install-rules        # пишет короткий блок в AGENTS.md/CLAUDE.md/правила .cursor
```

`install-guard` работает только там, где харнесс запускает за вас хук
PreToolUse. В остальных местах ничто ничего не применяет — поэтому
`install-rules` пишет короткий размеченный блок в тот из файлов `AGENTS.md`,
`CLAUDE.md` или `.cursor/rules/`, который уже есть в проекте (создавая
`AGENTS.md`, если нет ни одного), и объясняет агенту, как здесь пользоваться
maskrun. **Это указание, а не принуждение**: модель может его проигнорировать
так же, как любую другую инструкцию. Это запасной вариант для харнессов, до
которых `install-guard` не дотягивается, а не замена ему.

Блок ограничен маркерами `<!-- maskrun:start -->`/`<!-- maskrun:end -->`,
сначала делает резервную копию файла, идемпотентен (второй запуск обновляет его
на месте, а не дублирует), а `--remove` убирает его, не трогая остальной файл.
Если есть манифест `.maskrun`, блок перечисляет реальные имена переменных,
которые ожидает проект; `--file <path>` нацеливается прямо на один файл, минуя
поиск.

### Интерактивный режим

```bash
maskrun            # в вашем собственном терминале, без аргументов
```

Настоящий терминал, в командной строке которого больше ничего нет, открывает
режим навигации стрелками: слева платформы, справа секреты этой платформы и
подробности выделенного (платформа, заметка, значение).

```
↑↓ move   → enter   ← back   e edit   d delete   v reveal   y copy   q quit
```

Значения замаскированы (`••••••••••••••••`), пока вы не нажмёте `v`, и значение
читается из keyring только в этот момент — перемещение по списку его вообще не
трогает. Переход к другому секрету маскирует автоматически. `e` редактирует
платформу, заметку и значение на месте (пустой ввод оставляет текущее); `d`
запрашивает подтверждение по имени (`delete 'name'? [y/N]`), и продолжает
только буквальное `y`/`Y` — любая другая клавиша, включая Enter, отменяет. `y`
копирует значение в буфер обмена.

Он работает в [альтернативном экранном
буфере](https://en.wikipedia.org/wiki/Terminal_emulator#Alternate_screen_buffer):
ничто из того, что он рисует — включая раскрытое значение — никогда не попадает
в историю прокрутки вашего терминала, в отличие от нынешнего вывода
`maskrun get`. Это настоящее улучшение, независимо от всего, что идёт ниже.

Как и любой другой путь, касающийся значений, он **никогда не открывается в
сессии ИИ-агента** — с перенаправленным выводом или без, обнаруженная сессия
агента всегда получает ту же сводку только с именами, которую голый `maskrun`
печатает в неинтерактивном режиме. Он также отказывается работать в терминале
меньше 60x15 и сообщает причину, прежде чем откатиться к этой сводке.

#### Копирование в буфер обмена

`y` копирует текущий секрет в буфер обмена: раскрыть значение, которое потом
некуда вставить, — значит просто передвинуть проблему; вы бы набрали его
заново или выделили мышью, и то и другое хуже. Три встроенных ограничения:

- **Автоочистка через 45 секунд.** Как только что-то скопировано, TUI
  показывает живой обратный отсчёт; `c` очищает немедленно, не дожидаясь, а
  выход из TUI, когда что-то ещё скопировано, тоже очищает. Очистка
  восстанавливает то, что было в буфере до копирования, или опустошает его,
  если там ничего не было.
- **На каждой платформе отправляется подсказка «не записывать»** через
  `exclude_from_history` из arboard: MIME-тип KDE
  `x-kde-passwordManagerHint` в Linux, общепринятое соглашение
  `org.nspasteboard.ConcealedType` в macOS и нативный формат буфера обмена
  `CanIncludeInClipboardHistory` в Windows. Проверено здесь на настоящем
  Klipper: обычная копия появляется в его истории, помеченная — нет, и Klipper
  даже не сообщает помеченную как *текущее* содержимое буфера обмена. Каждое из
  этого — подсказка, которую конкретный инструмент сам решает соблюдать, а не
  то, что maskrun навязывает; см. ниже.
- Он **никогда не открывается в сессии агента** — тот же барьер, что и для
  остального TUI.

**Что это не чинит:** любой менеджер истории буфера обмена, который не ищет эту
подсказку (GNOME-овский, большинство не-KDE конфигураций Wayland и — это
наблюдалось напрямую при разработке — даже собственный Klipper от KDE, когда он
не следит за тем транспортом буфера обмена, который использует ваш композитор),
по-прежнему записывает значение навсегда, а 45-секундная автоочистка ничего не
делает с этой копией, раз она уже в файле истории. Относитесь к копированию в
буфер так же, как к `/proc/<pid>/environ` и к человеку, вставляющему
незамаскированное значение руками (ниже): это реальное ограничение, а не
решённая задача.

## Чем это не является

**maskrun не является границей безопасности.** Это укрепление против
случайностей, и его не следует продавать вам — или вами — как нечто большее.

- **Keyring решает вопрос хранения, а не доступа.** Любой процесс, запущенный
  от вашего пользователя, может вызвать `secret-tool lookup` или
  `security find-generic-password`, включая вашего агента. Тормоз повышает
  цену сделать это случайно; он не делает это невозможным. То же касается и
  вас: если человек вручную вставит незамаскированное значение в транскрипт,
  ни один инструмент после этого нажатия его уже не поймает.
- **Код, который тормоз не может прочитать.** Тела heredoc и файлы скриптов
  трактуются как данные, а не как команды — намеренно, потому что их разбор
  давал ложные срабатывания. Так что скрипт, который сам читает `.env` из
  собственного исходника, пройдёт. Сопоставление по шаблонам никогда не ловит
  произвольный код.
- **Окружение процесса.** Пока работает `maskrun run`, окружение его дочернего
  процесса читается через `/proc/<pid>/environ`. Тормоз блокирует этот путь
  напрямую, но внедрение через окружение по своей природе устроено именно так.
- **Автоочистка не отменяет копирование в буфер обмена (`y` в интерактивном
  режиме).** 45-секундный таймаут опустошает *буфер обмена*; он ничего не
  делает с менеджером истории, который уже записал значение навсегда до его
  срабатывания. maskrun помечает копию, чтобы KDE-шный Klipper её пропускал —
  это реально и проверено, но не каждый инструмент, ведущий историю, соблюдает
  эту пометку, и про историю буфера обмена GNOME, большинство не-KDE
  конфигураций Wayland и «Журнал буфера обмена» Windows такого не известно. Та
  же полка, что и `/proc/<pid>/environ` выше и человек, вставляющий
  незамаскированное значение руками, ниже: ограничение, названное прямо, а не
  тихо «решённое».
- **`ps` во время записи — закрыто.** В macOS значение раньше попадало в
  `security` как аргумент командной строки и на мгновение было видно в списке
  процессов через `ps`. Этого пути больше нет: maskrun теперь напрямую вызывает
  API generic-password из Security.framework, так что значение никогда не
  становится argv, который ОС обязана кому-то показывать.
- **Сопоставление по сегментам конвейера, а не разбор шелла.** Тормоз
  оценивает каждый сегмент конвейера по отдельности — именно это пропускает
  `sed 's/maskrun get/x/' notes.md`: этот текст никогда не вызывает
  `maskrun get`, он лишь его упоминает. Та же область видимости означает, что
  тормоз не следует за командой через косвенность: `echo 'maskrun get x' | sh`
  читается как `echo`, а не как команда, которую в итоге выполнит `sh`.

Если вам нужна настоящая граница, оболочка агента должна работать там, где она
вообще не достаёт до keyring — без сокета сессии D-Bus в Linux, под отдельной
учётной записью или в контейнере. Тогда maskrun работает из вашего терминала, а
не из агентского. Радиус поражения лучше ограничивать на стороне провайдера:
отдельный ключ на каждый инструмент, лимиты трат, ротация и короткоживущие
учётные данные там, где они есть.

## Бэкенды

| Платформа | Имя бэкенда | Хранилище |
|---|---|---|
| Linux | `secret-service` | Secret Service из libsecret, напрямую по D-Bus (крейт `dbus-secret-service`) — gnome-keyring, KWallet, KeePassXC |
| macOS | `keychain` | login keychain через API generic-password из Security.framework (крейт `security-framework`) |
| Windows | `dpapi` | Диспетчер учётных данных Windows (крейт `windows`, `Win32_Security_Credentials`) — имя сохранено от старого бэкенда на файлах DPAPI ради совместимости переопределения; хранилище под ним больше не файлы DPAPI |

Ранние версии на каждую операцию вызывали `secret-tool` в Linux и `security` в
macOS как подпроцесс, а в Windows вручную реализовывали хранение в файлах
DPAPI. Все три теперь для `put`/`get`/`delete` идут через библиотечную привязку
к API платформы, а не через подпроцесс или самописную криптографию — в Linux не
нужна установка `secret-tool`, а в macOS значение секрета больше не становится
аргументом командной строки. (В macOS `list` по-прежнему вызывает
`security dump-keychain`, чтобы перечислить имена — этот вызов не принимает
значение секрета аргументом, так что ничего нового не раскрывается; в
`security-framework` нет ограниченного сервисом вызова перечисления, которым
его можно было бы заменить.)

Хранилище в Linux сохраняет схему, которую ожидает
`secret-tool lookup service maskrun name <name>` (атрибуты `service` +
`name`), так что секрет, сохранённый maskrun, по-прежнему читается стандартным
CLI, если вам нужно проверить вручную — просто сам maskrun больше не зависит от
того, установлен ли этот CLI.

### Где хранятся метка платформы и заметка

| Платформа | Где |
|---|---|
| Linux | Два дополнительных атрибута Secret Service, `platform` и `note`, рядом с существующими `service`/`name` — `secret-tool lookup` сопоставляет только по тем атрибутам, которые вы ему дали, так что эти едут «попутчиками», ни на что, уже читающее `service`+`name`, не влияя. |
| macOS | Поля `kSecAttrDescription` (платформа) и `kSecAttrComment` (заметка) у generic password, записываются и читаются через API поиска по атрибутам и обновления только атрибутов из `security-framework` — само сохранённое значение при смене метки не затрагивается. |
| Windows | Оба закодированы в единственное поле `CREDENTIALW.Comment`, которое предлагает Диспетчер учётных данных (`platform=<p><US>note=<n>`, `<US>` = U+001F): отдельного хранилища атрибутов здесь нет, и смена метки вынуждена переписывать всю запись (вместе со значением), потому что у `CredWriteW` нет вызова частичного обновления. |

Переопределить определение бэкенда:
`MASKRUN_BACKEND=secret-service|keychain|dpapi`.

### Что действительно проверено

Все три бэкенда прогоняются в CI против настоящего keyring: Secret Service в
Linux, Keychain в macOS, Диспетчер учётных данных в Windows. Тесты keyring
записывают и считывают обратно настоящий секрет, а не подменяют бэкенд заглушкой,
а задание вообще без установленного keyring доказывает, что тормоз всё равно
отвечает.

С меткой платформы и заметкой та же история: прогнаны против настоящего Secret
Service в Linux (включая проверку совместимости `secret-tool` и схемы
атрибутов), проверены по типам кросс-сборкой для macOS и Windows так же, как
остальной платформенный код, но реально выполнены против настоящего Keychain
или Диспетчера учётных данных будут лишь тогда, когда эти задания CI запустятся.

Самый первый запуск CI, который вообще стартовал, нашёл три настоящие ошибки в
платформенном коде — все на путях, которые сборка под Linux никогда не проверяет
по типам, потому что они за `cfg`: два аргумента Win32 неверного типа, вызов
`CredEnumerateW`, передающий одновременно фильтр и флаг «все учётные данные»
(вместе недопустимы), и сравнение `ERROR_NOT_FOUND` с сырым кодом Win32 вместо
`HRESULT`, который приходит на самом деле — из-за чего отсутствующий секрет и
пустое хранилище оба всплывали как сырая ошибка. Задание линтинга теперь
кросс-проверяет цели Windows и macOS из Linux, чтобы этот класс ошибок больше не
доходил до платформенного раннера.

Что *не* покрыто: тесты обработки блокировки включаются явно
(`MASKRUN_LOCK_TESTS=1`), потому что запуск одноразового
`gnome-keyring-daemon` на настоящем рабочем столе просит пользователя создать
keyring и переживает сам тест.

## Команды

```
maskrun put <name>                    store a secret (prompts; not echoed)
maskrun put                           fully interactive: asks name, platform, note, value
maskrun put <name> --stdin            store from stdin (for scripts)
maskrun put <name> --for X --note Y   tag it with a platform and a note while storing
maskrun label <name> --for X          tag (or retag) an existing secret's platform
maskrun label <name> --for ""         clear its platform
maskrun get <name>                    print it (refused in an agent session)
maskrun list                          grouped by platform, with notes, never values
maskrun list --plain                  flat, sorted names only, one per line (for scripts)
maskrun rm <name>                     delete (no name: pick from a numbered list)
maskrun status                        check the manifest against the keyring
maskrun run [--raw|--mask] -- CMD     run with the manifest injected
maskrun exec VAR=name -- CMD          run with explicit pairs, no manifest
maskrun -- CMD                        shorthand for run
maskrun import <.env> [--dry-run]     move a .env into the keyring
maskrun completions <fish|bash|zsh>   print a shell completion script
maskrun install-guard [--remove]      register the agent guard
maskrun hook                          the guard itself (reads JSON on stdin)
maskrun install-rules [--remove]      tell agents how to use maskrun here (guidance, not enforcement)
```

`import` пропускает переменные `VITE_`, `NEXT_PUBLIC_`, `PUBLIC_`,
`REACT_APP_`, `NUXT_PUBLIC_`, `EXPO_PUBLIC_` и `GATSBY_`: они компилируются в
клиентский бандл и отправляются каждому посетителю, то есть это конфигурация, а
не секреты, и переносить их незачем. `--all` отменяет это поведение.

### Метки платформ и заметки

Когда секретов становится больше горстки, плоского имени уже не хватает, чтобы
помнить, для чего каждый — особенно когда у одной платформы несколько ключей и
отличаются они областью действия, а не именем. `--for` помечает секрет
платформой или сервисом; `--note` добавляет короткое описание свободным
текстом:

```
$ maskrun put gh-release-token --for github --note "fine-grained, contents+plan"
stored: gh-release-token

$ maskrun label vault-token-github --for github --note "fine-grained, repo+plan"
labelled: vault-token-github

$ maskrun list
github
  gh-release-token       fine-grained, contents+plan
  vault-token-github     fine-grained, repo+plan
(no platform)
  pos-terminal-electron-api-url
```

Оба флага необязательны и применяются к секретам, у которых пока нет ни того,
ни другого. `label` перемечает существующий секрет задним числом; в любой из
этих команд `--for ""` (или `--note ""`) очищает соответствующее поле, а
полностью опущенный флаг оставляет текущее значение как есть — `put` поверх
значения секрета никогда не теряет его метку молча. **Платформа и заметка не
являются секретами**: они хранятся без маскирования, видны в сессии ИИ-агента и
показываются в `list` и `status`. Не кладите значение секрета в `--note`; поле
ограничено 200 символами и не может содержать перевод строки.

`maskrun` без аргументов открывает [интерактивный
режим](#interactive-view) в настоящем терминале; при перенаправлении
(`maskrun | cat`), в неинтерактивном режиме или в сессии агента он вместо этого
печатает короткую сводку: состояние манифеста и сгруппированный список секретов
выше, чтобы вам не приходилось держать в голове всю поверхность команд.

### Автодополнение оболочки

```bash
maskrun completions fish > ~/.config/fish/completions/maskrun.fish
maskrun completions bash > ~/.local/share/bash-completion/completions/maskrun
maskrun completions zsh > ~/.zfunc/_maskrun   # затем `fpath+=~/.zfunc` до compinit
```

Помимо флагов и подкоманд, `maskrun get`/`rm`/`label` дополняют реальные имена
секретов — fish делает это из коробки (через тот самый `maskrun list --plain`,
ради которого этот флаг и существует); bash и zsh получают только статические
дополнения.

## Переменные окружения

| Переменная | Действие |
|---|---|
| `MASKRUN_MASK` | `1` всегда маскировать, `0` никогда не маскировать |
| `MASKRUN_AGENT` | `1` считать это сессией агента, `0` считать человеком |
| `MASKRUN_BACKEND` | принудительно выбрать бэкенд |
| `MASKRUN_ALLOW_READ` | `1` снова включает `get`/`import` в сессии агента |

Сессии агента определяются по `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`,
`AI_AGENT`, `AIDER_CHAT`, `CURSOR_AGENT`, `OPENAI_CODEX`, `GEMINI_CLI` и
`REPLIT_AGENT`. Для всего остального задайте `MASKRUN_AGENT=1` в харнессе.

## Поддержка платформ

- **Linux** — glibc 2.35 или новее (релизные бинарники собираются на Ubuntu
  22.04). Протестировано в CI против работающего Secret Service.
- **macOS** — Intel и Apple Silicon. Протестировано в CI против настоящего
  Keychain.
- **Windows** — x86_64. Протестировано в CI против настоящего Диспетчера
  учётных данных.

## Предшественники

[`envchain`](https://github.com/sorah/envchain) клал секреты в keychain и
внедрял их в окружение ещё годы назад и является прямым предком той половины
этого инструмента, что отвечает за `run`. [`direnv`](https://direnv.net/)
управляет окружениями по каталогам, [`sops`](https://github.com/getsops/sops) и
[`dotenvx`](https://github.com/dotenvx/dotenvx) шифруют секреты при хранении в
репозитории, а [`aws-vault`](https://github.com/99designs/aws-vault) исполняет
танец с keychain для одного провайдера.

Что добавляет maskrun — это половину, обращённую к агенту: маскирование вывода
дочернего процесса и применяемый харнессом тормоз на командах, которые выдали
бы значение. Если вы не работаете с ИИ-агентом, вам, возможно, хватит
`envchain`.

## Разработка

```bash
cargo test -- --test-threads=1   # в один поток: бэкенды делят реальное состояние keyring
cargo clippy --all-targets -- -D warnings
cargo fmt --check
make test                        # тот же прогон тестов
make lint                        # fmt --check + clippy
```

Тесты keyring пропускают сами себя, когда ни один бэкенд недоступен, чтобы
тесты тормоза всё равно выполнялись в голом контейнере.

Секретные значения в тестовом наборе генерируются случайно и никогда не
печатаются — утверждения проверяют отсутствие или присутствие, но никогда не
равенство с залогированным значением.

Вклад приветствуется. Добавить бэкенд — значит реализовать
`put`/`get`/`delete`/`list` трейта `Backend`; добавить харнесс — значит одну
запись в `integrations/`.
